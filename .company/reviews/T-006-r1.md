## Loop / runaway analysis
- refresh -> prefetch -> refresh: an id goes into `this._prefetched` synchronously, before the `AboutToShow` await, so concurrent refreshes cannot send a second call for the same id. A follow-up `refresh()` only runs when at least one new id was sent. Recursion is bounded by the number of distinct empty-submenu ids.
- LayoutUpdated during prefetch: N prefetched ids cause about N signal-driven `GetLayout` calls plus 1 follow-up. Each one re-walks the tree but finds no new ids. `onChanged` callbacks are coalesced through the existing `_refreshQueued` idle. The cost is bounded and linear (about 11 GetLayout calls for a 5-menu Electron app at startup). Nothing runs away.
- On-open path (`item.aboutToShow`) still sends AboutToShow + `opened` and then refreshes. That refresh can prefetch newly revealed nested ids, still at most once each.

## Placeholder safety
- `fillMenu` adds `Loading…` only when no item survives (after hidden items, separators and the trailing separator are dropped). The Apple/application menu and the standard File/Edit/View/Window/Go menus always have visible static items, so they never get it.
- GtkMenuSource: a submenu that is truly empty now shows an insensitive `Loading…` row and no longer refuses to open. This is harmless: the row is insensitive and not reactive, and `CascadeMenuItem`'s Right-key handler uses `find(i => i.reactive)`, which safely returns undefined.
- In-place refill (`_onSourceChanged` -> `fillMenu`) calls `removeAll()` first, so the placeholder is replaced and never piles up.

## Non-blocking suggestions
1. menuSources.js:241-255 — A submenu that stays empty after AboutToShow (for example an empty "Recent" list) shows `Loading…` forever. Consider an insensitive `(Empty)` label once that id is in `_prefetched` and the on-open AboutToShow has already run.
2. menuSources.js:241 — Hardening: if an app ever rebuilds the whole tree with fresh ids on every AboutToShow, the per-id set would not stop prefetching. A small cap (for example at most 3 nested prefetch rounds per signal-free burst, or a total limit) would guard against that. Not needed for the Chromium behaviour seen live, where parent ids are stable.
3. menuSources.js:226 — Signal-driven refreshes are not coalesced. Debouncing `refresh()` (one in flight plus one queued) would cut the burst of N GetLayout calls down to about 2.
4. Pre-existing, out of scope: `_onSourceChanged` refills the merged app menu (index 0) with only `top[0].children` and drops the Hide/Quit items until the next rebuild.
